# ng-orbit Voice and Copy

This note is for product docs, previews, and demo copy inside the repo.

## Voice

- Warm precise: human, calm, and technical without sounding stiff.
- Outcome first: start with what the reader gets, then explain how it works.
- Active voice: prefer "your app handles the data" over passive ownership language.
- Boundary clarity: always make it obvious what ng-orbit does and what still belongs to the app.

## Preferred language

- Say `your app`, `your team`, `your UI`, or `your feature`.
- Use `headless`, `renderer`, `adapter`, `contract`, and `query` only when they add real clarity.
- Keep package names, API names, and code terms in their original form.
- In Spanish, prefer natural phrasing with selective English product terms instead of literal translation.

## Avoid

- Repeating `consumer`, `surface`, `stable contract`, or `integration layer` in every paragraph.
- Copy that sounds like a legal boundary document.
- Hype, buzzwords, or "magic" language.
- Explaining the same ownership rule three times in slightly different words.

## Writing pattern

- Summary: what it helps you build, then who stays in control.
- Tagline: how to start using it without overselling it.
- API descriptions: plain explanation first, exact boundary second.
- Examples: describe the scenario in product terms before naming the technical event or directive.

## Quick examples

- Better: `Build tables around your own data flow and UI.`
- Worse: `A headless table controller for consumer-owned rendering surfaces.`

- Better: `Your app still handles submit, autosave, and business rules.`
- Worse: `Business-side side effects remain consumer-owned responsibilities.`
